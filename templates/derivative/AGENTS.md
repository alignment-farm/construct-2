# Instructions for the derivative agent

Template: Construct-2 working agreement v0.1. Adapt paths and project-specific
instructions before adoption; retain existing instructions that still apply.

## Read and own the task

Read `README.md`, `notes/CHARTER.md`, the active protocol and amendments, the
latest evidence return, and `notes/HANDOFF.md` if present. The charter identifies
the root question, assignment, allowed resources, and completion criteria.
Inspect Git status and active runs before editing or launching work. Preserve
other contributors' changes. Resume from the recorded state rather than
repeating completed setup experiments.

Own implementation, documentation, meaningful tests, instrument repairs,
execution, and evidence reports within the assigned scope. Resolve routine
choices autonomously. Use `uv` for Python dependencies and environments, and
Docker for local model/resources as specified by the project. Do not change
another derivative or reconfigure a shared model service without an assignment
covering it. This file does not assign additional agents or grant a new budget.

## Preserve the experiment

- Freeze and record actual source, protocol, configuration, data, model, and
  observable backend/template identity before model contact. Record exact
  requests and distinguish requested settings from verified behavior.
- Validate the roles and paths the claim uses. Fake endpoints and short format
  probes do not establish real-model workload performance. Check outcomes
  independently of the tested model's self-assessment.
- Follow the protocol's evaluation isolation, stopping, retry, and recovery
  rules. Keep every attempted call in the ledger, including failures and
  separate probes. Preserve raw outputs, inputs, state, and earlier analyses.
- Document repairs and amendments, including outcomes already seen and effects
  on comparability. Version reanalysis; do not silently rescore, replace draws,
  use evaluation feedback to improve a frozen treatment, or restart a stopped
  run to erase its failures.
- Bring a concrete amendment to the root/user before inference that changes
  the scientific comparison or exceeds the charter. Continue independent work
  while a decision is pending. Implementing a repair alone does not authorize
  new calls or a changed treatment.

## Return evidence and leave a usable project

Use a progress report for a milestone, consequential surprise, or decision.
Use a final report at the charter's endpoint or a stop that prevents completing
it. Keep reports in `notes/returns/`, with links to the protocol, run IDs,
source pins, raw evidence, analyses, counts, costs, and counterexamples. State
what remains untested and what changes in the root question.

Commit the report and evidence; give the user the repository, full return
commit, report path, status, and specific decision if needed. Do not send
messages or edit the root repository without explicit assignment. Respond to
review through a new report/revision that preserves the original record.

Keep the README/handoff accurate about the next action, remaining budget,
active processes, and stopped or parked work. Cleanup improves navigation and
marks superseded material; it preserves failures and provenance. A successful
diagnostic does not authorize the next study unless the charter already does.
