## Question and starting point

> When an agent already retains its working program, tests and source history,
> does additional processing of earlier experience improve complete work on a
> later unfamiliar change? What does that improvement cost?

The [program synthesis](CONTINUING_CAPABILITY.md) distinguishes useful code from
additional experience without assuming they can always be separated. A regression
test, an explanation and an adapter can each preserve something learned. The
question is what a particular investment adds, not whether one condition deserves
the label “memory.”

Use ETL maintenance as the first development lead: acquire validation and linear
execution, then extend to branches and named sub-pipelines. Code search provides
a second lead with a later transition into file edits. Both have inspected,
passing reference assets; no participant acquisition is established. Start from
the [pinned sources and checks](../sources/2026-09-20-task-sequences/README.md).
The investigator owns final workload choice, feedback, protocols and execution.

The new [methods reading](../sources/2026-09-20-experience-comparison/README.md)
adds P98–P100. It identifies a later real-repository candidate and sharpens the
distinction between inherited state, resource allowances and observed outcomes.
Generic continual coding or another memory framework is not the proposed novelty.

## Cross-session learning target

The concrete starting target is an acquired investigation procedure: find relevant
earlier evidence, inspect affected code, choose a discriminating test and use its
result to repair a program under a later unfamiliar requirement. Begin with a
trainable tool-using model and a retained LoRA adapter. The investigator selects
the model and teaching method through bounded development. Acquisition and fresh
complete behavior come first; costs qualify their practical value. Software
maintenance is the test setting, not a replacement research directive.

Start fresh model conversations and reset ephemeral runtime state between task
episodes. Inventory retained workspace, tests, notes, source experience and
condition-specific learned state. Verify isolation and base/adapter loading;
provider conversation state or inference caches must not silently carry the
experience. Record what survives each reset. Between-session processing uses
only eligible earlier experience, before the next requirement is revealed.

## A small initial comparison

All conditions receive the same current requirements and ordinary tools. Each
retains the program, its own tests and notes, and the eligible source archive.
The archive includes prompts, visible feedback, attempted changes and tool
results—not hidden reasoning unavailable from the provider. Ordinary inspection,
search, repair, caching and preservation of new artifacts remain legitimate.

| Condition | Additional investment | What the contrast can establish |
|---|---|---|
| Ordinary continuation | Uses retained artifacts and searchable experience as needed | A competent practical reference with actual costs |
| Between-session learning | Acquires the investigation behavior from eligible prior experience before the next requirement is revealed; retains the adapter | Value and cost of investing in advance |
| Ordinary continuation with extra allowance | Can spend the consolidation allowance on ordinary inspection, testing or repair after the next requirement arrives | Whether consolidation beats another useful allocation of that resource |

The third condition is an opportunity-cost comparator, not an exact mechanism
ablation: it spends its allowance later, when the new requirement is known.
Allow unused budget; padding the baseline with pointless calls would be invalid.
Choose a comparable allowance and record native costs. Equal token ceilings do
not equate different models, training and tool execution, or guarantee equal
consumption. Report quality against actual work as well as allowed work.

A source-linked aid describing what earlier attempts established can be a useful
comparator or diagnostic; it is not a prerequisite for the selected neural
treatment. Derive teaching and aids from the participant's eligible history.
Root's examples of parser or coordinate failures are possible phenomena, not
teaching material to insert. Freeze the developed treatment before testing the
next withheld change.

For the first matched-workspace diagnostic, fork the same acquired checkpoint-2
program, tests and ordinary notes. Keep that inherited state fixed across the
initial comparison. A consolidation treatment that edits the program or tests
belongs to a separate comparison that allows such artifact changes; those edits
are legitimate experience retention but change the attribution. Later continuing
comparisons can allow each policy to accumulate its own artifacts and failures.

If one policy receives useful material directly in its prompt while another must
search, the difference includes delivery. Record that fact. A positive result may
justify a small follow-up delivering source excerpts through the same route to
test whether the advantage comes from selection, representation or easier access.
This is a targeted diagnostic, not a required full factorial design.

## Developing the learned investigation

The selected adapter learns investigation and evidence use while the archive and
programs stay available. A small memory model that learns what to supply to a
fixed executor is another possible intervention, not the initial commission's
default. A justified change remains within the investigator's authority; keep
distinct interventions separate in claims about “the learned arm.”

A neural treatment need not wait for a prose-aid win. Develop the target through
an informative bounded acquisition comparison. Verify mutable-state access and demonstrate acquisition on
development work; finite gradients are insufficient. Include teacher generation,
failed training, validation and later repair in costs. Preserve the opportunity
to retain useful code even if doing so removes neural headroom.

The [weight follow-up](../studies/2026-09-18-continuing-consolidation-findings.md)
does not establish why fresh evidence use failed. A new learner should have
development opportunities to perform the behavior it is meant to improve;
training only final answers would not directly teach investigation. P42/P89 offer
compatibility methods, not a prescribed explanation or mandatory recipe.

## Prospective expectations

These expectations are new and untested. Preserve their wording when appending
assessments; AD, EX, WC and LA predictions retain their original boundaries.

- **CC1 — Residual experience value.** Added processing will be most useful when
  earlier work established a consequential reason, diagnostic or limitation that
  is difficult to recover from the current code and ordinary archive in time.
  Rephrasing an already explicit contract should add little. Compare complete
  later behavior and retrieval/repair effort, and inspect which source evidence
  explains any difference.
- **CC2 — Opportunity cost.** Some gains over ordinary continuation will disappear
  when it receives comparable extra resources for current-task inspection and
  testing. Advance consolidation should have a stronger case when its acquired
  contribution serves several later changes; repayment over that horizon remains
  to be demonstrated rather than assumed from one faster response.
- **CC3 — Artifact mediation.** In these short software sequences, part of any
  continuing-policy advantage will reside in better code and tests. An advantage
  with policy-specific workspaces need not survive a matched-workspace diagnostic.
  If it does survive, identify the additional retained contribution rather than
  attributing the whole sequence gain to it.

One outcome can narrow several expectations. An ordinary solution that explains
why the added treatment has no useful contribution is valuable. These small
sequences cannot establish a universal storage ranking, a general absence of
learning benefit, or performance over years of deployment.

## Evidence and bounded execution

Establish competent checkpoint-2 work before interpreting checkpoint-3 retention
or transfer. Preserve acquisition failures and diagnose plausible causes within
the stated resources. If a different model or harness supplies a functioning
comparison, explain the change and distinguish general capability improvement
from the effect of accumulated experience.

Decide the visible development feedback before collection. Participants can use
their own tests and agreed current-task feedback. Keep examiner solutions, future
requirements and confirmation tests outside their experience. Checkpoint 3 can
support diagnosis; checkpoint 4 is a subsequent change, not a new independent
history. A checkpoint used to revise the treatment is development material even
if it was originally called a test. Preserve unsuccessful cases and use fresh
material for the resulting claim.

Measure complete new behavior and still-valid earlier behavior, then whether both
hold together. Test counts and code metrics help diagnose a failure but do not
replace that outcome. Re-running a test after editing can be necessary; fewer
repeated calls alone is not success. Likewise, superseded requirements should not
be scored as forgotten obligations. Use snapshots so evaluation observes the
submitted state, and distinguish infrastructure failures from task failures.

Keep accounting small and sufficient: source collection and preprocessing,
delivered context, inference, retrieval, training, tests, repairs and elapsed time.
Charge shared acquisition consistently, distinguishing common costs from costs
that differ by policy. Report failed and incomplete runs as well as successful
ones. Compare by task/change and acquisition history; hundreds of overlapping
assertions are not hundreds of independent observations.

The investigator should publish what worked, what failed, what explains the
difference, and what further bounded step is worth taking. Continue useful
diagnosis within the remit; stop on explanatory progress, a demonstrated limit
or a concrete resource constraint. Do not keep expanding the harness merely to
avoid an informative ordinary-code result.
