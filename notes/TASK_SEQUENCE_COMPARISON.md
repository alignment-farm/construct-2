## Recommendation

Start with **SlopCodeBench's ETL pipeline**, with **code search and repair** as a
second setting if initial acquisition is practical. Keep **CL-Bench database
migration** as a reserve for a different question about revising acquired schema
knowledge. The two software sequences require extending an actual inherited
program and supply direct checks of new and preserved behavior. They offer a
shorter route to the selected comparison than building another environment.

These are existing **authored benchmark sequences**, not observed production
maintenance histories. They provide realistic operations and executable changes;
they do not establish ecological validity or independent-history generality.
Both software candidates come from the same benchmark. Their different domains
are useful variation, not independent evidence about every kind of continuing work.

The [artifact ledger](../sources/2026-09-20-task-sequences/README.md) records exact
revisions, file hashes, inspection limits and reproduction. Reference checks pass
for both software candidates. That establishes working examiner assets on this
host, not successful acquisition by a proposed learner or a benefit from memory.

## ETL: extending a program that already does useful work

The participant starts with a CLI specification and creates its own workspace.
Checkpoint 1 validates and normalizes pipeline requests. Checkpoint 2 adds
execution over JSON rows, including arithmetic, filtering, renaming, limits and
specified handling of missing values. Checkpoint 3 introduces conditional routing,
nested branches and branch-order concatenation. Checkpoint 4 introduces named
definitions, parameter binding and recursion rejection. A fifth library-composition
checkpoint exists; only its interface was surveyed, not executed in this review.

The useful initial boundary is a functioning checkpoint-2 implementation. A
participant could already have encountered parser defects, mistaken treatment of
missing fields, or incorrect normalization. Branches then require those behaviors
to work inside nested execution. Calls require them to survive another change in
scope and error reporting. These are opportunities for experience reuse, not
lessons to supply as a teacher-written answer.

A competent ordinary solution can inspect the current program, requirements,
source history and its own tests, then extend existing components and preserve
the improvements. The comparison must permit that. If the implementation and
regression tests already encode everything useful, additional curation may
correctly have no advantage.

The published checkpoint-3 implementation passes **117/117** tests spanning
checkpoints 1–3. Checkpoint 4 passes **134/134** spanning 1–4. These checks exercise
results and failures, including routing and nested error behavior. They are
repeat executions of overlapping suites, not 251 independent tasks. They do not
prove the specifications or tests exhaustive. The inspected CLI needs Python
and JSON Schema support; no external service or model is needed to evaluate it.

## Code search: moving from observation to edits

The initial program finds exact and regular-expression matches in Python files.
The next change adds JavaScript and C++ with language filtering. Checkpoint 3
adds structural patterns, repeated/optional metavariables and capture ranges.
Checkpoint 4 adds node selectors, replacement templates, preview/apply modes and
overlap handling. This gives a materially different later obligation: correct
printed matches are insufficient once the tool modifies files.

Earlier work could expose mistakes in source coordinates, repeated captures or
match ordering. Later editing can make those mistakes consequential. Ordinary
inspection and a retained parser are strong alternatives; a memory treatment
must help beyond them. Retaining a competent parser library is legitimate.

Published implementations pass **47/47** checkpoint-1–3 checks and **75/75**
checkpoint-1–4 checks. The tests include checking actual file contents and that
preview mode does not write. The reference uses pinned Tree-sitter packages,
which installed and ran on this ARM Mac. The full Docker agent runner was not
installed or exercised. The benchmark's “Easy” label does not establish that
the available learner can acquire structural matching within a useful budget.

## Database migration: a useful reserve with a different target

The pinned upstream schedule uses twenty pre-migration and twenty post-migration
questions. Within-stage ordering can vary; the three product groups share a
single database history. An illustrative dependency chain is electronics price
and price/review work (**q9, q12**) followed after migration by filtered prices,
relative-price counts and price/review composition (**q101, q103, q105**). This
is a selected subset of actual instances, not their default scheduled order.

The normal interface permits exploratory SQL and returns query results/errors.
It announces possible change and can reveal the correct answer after an incorrect
submission. Earlier SQL, observations and any acquired helpers should remain
available. Supplying investigator-normalized views would again remove much of
the discovery target identified in the [previous assessment](../studies/2026-09-18-continuing-consolidation-findings.md).

Five selected reference queries reproduce their published answers on hash-verified
databases. Replacing the new price column with the obsolete column in three
post-migration queries changes all three results, yet the numeric grading rule
would accept **two of those three selected stale results**. This is not an
estimated benchmark-wide defect rate. Approximate-answer tolerance can be
appropriate for the upstream metric while failing to establish a correct reusable
computation. Our question would need program-level checks and discriminating data,
with intended semantics resolved independently of the submitted program.

Unlike software evolution, this task does not require preserving and extending
a delivered program. Adding that obligation and checks for still-valid behavior
would be a declared adaptation. The cached snapshots total about 830 MB; selected
SQLite queries run locally. Full framework integration and an independent
database history remain untested. Its existing local exposure also makes it a
poor sole source of fresh confirmation.

## Proposed bounded comparison

Use the first two checkpoints to acquire useful work, then examine the next
change. Give the primary comparator working code, earlier requirements, ordinary
tools and a searchable archive of its actual attempts, tool results and feedback.
Allow it to preserve code, tests, notes and later reconstructions. Give the
additional-memory condition the same eligible sources and account for whatever
curation or learning it performs. A deliberately empty archive is only an
information-value diagnostic, not the main alternative.

For a matched-workspace diagnostic, fork an acquired checkpoint-2 state before
checkpoint 3. Compare complete new behavior, earlier valid behavior and total
work. This identifies the contribution of extra experience processing given the
same program. A later continuing comparison can carry each policy's own artifacts;
its result also includes the consequences of earlier artifact choices. Do not
describe these two estimands as interchangeable.

The published protocol hides official tests and feedback. For ordinary maintenance,
participants should retain their own tests and receive agreed development feedback.
Before a pilot, the investigator should specify which existing checks become
visible and which remain examiner-only, equally across treatments. A visible
development suite plus independent confirmation checks would change the upstream
protocol and should be reported as such. Published solutions and future tests
are examiner assets, never retrospectively acquired participant experience.

Checkpoint 3 is suitable for diagnostic development; checkpoint 4 is a different
change that can support subsequent confirmation once treatments are frozen.
It is still within the same project, not proof of transfer to a new domain.
Code search supplies a second domain if feasible. Additional numerical seeds
alone do not create independent histories; record the actual acquired programs,
mistakes and revisions, and distinguish independent acquisitions from independent
task sequences.

Measure new and preserved complete behavior separately, then the combined useful
outcome, along with acquisition, retrieval, curation/training, test, tool and repair
costs. Preserve model/version, prompts, dependencies, allowed feedback, snapshots
and failures. No model cost estimate is established by the few seconds needed for
reference tests. Token, wall-time and training costs should remain distinguishable.

The first uncertainty is whether prior experience has useful value beyond the
shared code and ordinary archive, and whether the learner can first do the work.
Explicit records, acquired procedures and weight updates remain eligible; this
selection does not decide their ranking. If an inexpensive condition already
solves the changes, that is explanatory progress. If acquisition fails, diagnose
the failure within a stated budget before interpreting retention or transfer.

An ancillary investigator would own that pilot, its protocol and any justified
workload changes. Construct Runtime is optional instrumentation; these CLI
interfaces do not require a new runtime build. Completed ancillary phases,
original predictions and the root's fixed directive remain unchanged.
