# What does retaining implementation buy?

17 September 2026. Root development after the [completed artifact review](../studies/2026-09-17-executable-feasibility.md).
**Keep the bounded independent allocation question, but strengthen its
reconstruction alternative and narrow the claim.** Newly inspected public work
already compares retained skills with disposable scripts. A useful local study
would ask what retaining implementation adds to the same acquired procedural
experience, with complete outcomes and all incurred work counted.

This note was written as scientific preparation. The subsequent commission is
recorded below; the ten accepted ancillary phases remain complete. EX1–EX3 in
[the original selection](EXECUTABLE_EXPERIENCE.md)
and AD1–AD3/EU1–EU3 retain their wording and assessments.

## What the additional reading changes

The [versioned source ledger](../sources/2026-09-17-persistence-controls/README.md)
adds P71–P74 and a pinned SkillCraft inspection. SkillCraft's Direct Exec arm is
a closer precedent than the earlier donor search captured. Its current release
provides generated scripts, shared tool access and debugging feedback, although
paper descriptions of the arm conflict. CodeMem explicitly proposes avoiding
reconstruction through retained functions. PANDO develops online maintenance;
Skill Blocks supplies a more efficient contextual alternative. These are different
evidence types, with limits recorded in the ledger.

The selection consequence is substantive: a library-versus-atomic-tools result,
an ephemeral-code arm, adding demotion, or counting induction cost would not by
itself add the intended knowledge. SkillWeaver remains a donor for acquired
browser routines; SkillCraft adds a donor for programmatic tool chaining.
Neither is a required platform or an already matched experiment.

## Three effects, with different comparisons

| Effect | Comparison that can inform it | What it cannot establish alone |
|---|---|---|
| Running a tool chain outside the model's context | Primitive calls versus generated executable code with the same task evidence | A benefit of retaining code across sessions |
| Avoiding reconstruction of an acquired procedure | Retained implementation versus competent generation from procedural experience | Whether code preserved information missing from the alternative |
| Choosing what experience to retain | Implementations versus lessons/examples built from a common acquisition history | A pure invocation effect, since abstraction and access also change |

The previous artifact assessment usefully proposed regeneration with the same
source available as a diagnostic. There is an additional boundary: if both arms
may read and execute identical source, an ordinary loader or copy can install
it. Requiring an LLM to rewrite that source would manufacture avoidable work.
Such an arm can measure an interface's installation or invocation overhead;
it is not automatically a serious deployment alternative or an isolated semantic
reconstruction cost. Permit the competent solution and accept a tie.

Conversely, source appearing in an old trajectory or workspace log remains
accessible implementation even without a registered library. SkillCraft makes
this distinction concrete. A text-memory treatment retaining those logs is not
code-free. If source remains in a recoverable archive, describe the comparison
as keeping code ready versus recovering it, and charge actual recovery. If only
lessons and examples survive, their construction and omissions become part of
the representation comparison. The investigator should choose which allocation
matters; neither silent erasure nor hidden source access identifies it.

These deductions sharpen the existing hybrid hypothesis. A program, a description
of its purpose, evidence of its successful use and current facts can each carry
different parts of the maintained capability. Representation and delivery need
not be the same decision. This is an analytical account, not a new measured effect
or a universal prescription to retain every object.

## The smallest useful independent investigation

Start with a reproducible recurring operation for which an agent can acquire
a functioning implementation and a developed contextual alternative can also
generate and execute useful behavior. Workload discovery belongs to the study;
large browser infrastructure is optional. Supplied primitive tools, labels,
schemas and correction authority must be visible in the claim.

Use a common acquisition record to build the retained objects. Preserve failed
attempts and the evidence supporting any repair. Give both alternatives current
observations, an executor and access to the same acquired tests or verification
procedure. This estimates implementation value **conditional on that checking
capability**; it does not show that tests or their acquisition are free. A quality
warning present only in the library route is an additional intervention. Shared
benchmark answers remain evaluation evidence, not free runtime feedback.

The serious contextual alternative can keep concise lessons, examples and known
failure cases, load relevant parts, use available prompt caching, generate code,
inspect results and repair. The retained implementation can take current facts as
parameters, use conditional observations and receive local repair. Neither must
be frozen after the first error. Common acquisition may cancel from a marginal
comparison, but a total acquisition-repayment claim must still count it and each
arm's subsequent construction, checking and selection. A supplied successful
library supports a marginal-use comparison only unless its acquisition is known.

First establish stable-use quality and actual work. Then, if informative within
the resource scope, assess a consequential revision. Distinguish a changed input
value that a valid procedure already accepts, an interface change that can be
locally repaired, and a change in required behavior. A parameter update to explicit
facts need not require either code or weight repair. A changed obligation may
invalidate a historical test; keeping that test authoritative would score correct
revision as failure.

Do not require a full factorial or a learned chooser. The researcher can use
development to find an identifying contrast and then fresh requests to assess
the resulting claim. Failed acquisition warrants diagnosis; if competent
regeneration already makes retention redundant, that is a useful explanation.

## Quality and cost must describe the same sequence

For a fixed sequence, retain complete successes and paired failures alongside
costs from every request, including failed construction, checking and repair.
Success-conditioned timing answers how much common successes cost; it cannot
by itself establish deployment savings. With different success sets, two such
averages need not even concern the same requests. Partial-credit benchmarks
can remain useful diagnostics, but their success threshold must not become a
claim that every required consequence was correct.

Record model input, cache reads, generated output, calls, executed primitives
and elapsed time separately where available. A cache discount can be a disclosed
sensitivity; it cannot establish measured latency or billing. Savings from
prompt delivery or moving intermediate data outside context belong in the system
comparison, but are not automatically savings from cross-session persistence.
Full study search costs and the costs of one selected deployment remain distinct.

## Priority and closure

| Candidate investment | Root decision |
|---|---|
| Another generic library-versus-primitive demonstration | Already substantially answered; not selected |
| Fix AWM or reproduce a large benchmark solely to obtain an execution arm | Existing donors now suffice; not selected |
| Further adapter training or a larger maintenance selector | Current publications do not give these automatic priority |
| Shared-experience retention versus competent reconstruction | Keep as the recommended bounded independent investigation |
| Controlled repair or retained verification as a separate treatment | Conditional follow-up only if stable-use evidence makes it consequential |

The preparatory literature question is closed: there are concrete donors and
closer public comparisons, with identifiable limits. Further generic donor
search has low value. The next useful empirical contribution would locate a
boundary where preserving implementation changes complete behavior or actual
work beyond efficient reconstruction, or explain why it does not. Choosing and
running that workload belongs to an ancillary investigator if commissioned.
This root update neither launches that study nor certifies an unexplored gap.

## Resolution of the stable-use comparison — 17 September

The [publication assessment](../studies/2026-09-17-executable-retention-findings.md)
advances the boundary to `baf4d764cb4e571551a2b69d45751bb7f3281eaf` and accepts
the bounded phase. On eight fresh requests, all policies are complete. Direct
source recovery matches ready source with no generation; retaining the first
reconstruction removes later generation. Repeated reconstruction is costly under
the disclosed source-discard policy, not an unavoidable property of contextual
experience. The complete contract remains available and the marginal value of
the acquired prose is untested.

Shared checks and API reads, preserved timeouts and paid lesson repair support
the specified cost comparison. Full engineering costs and general reliability
remain unmeasured. The root [check ledger](../sources/2026-09-17-executable-retention-review/README.md)
records independent rescoring and accounting. This resolves stable reuse enough
for closure; interface repair, autonomous applicability and learned retention
decisions are broader questions rather than a commissioned second phase.
